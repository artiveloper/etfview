# QA Backend Strategy

> 프로젝트 특이사항 절의 대상: `collector/` 서브프로젝트. 경로 언급은 `collector/` 기준 상대경로다.

특정 기술·프로젝트에 종속된 검증 항목은 이 스킬에 넣지 않고 별도 기술 스킬로 분리한다. 이 스킬은 스택 불문 테스트 전략 판단 기준만 다룬다.

## 테스트 피라미드 판단 기준

- **단위 테스트**: 순수 로직(계산, 파싱, 검증 규칙 등)에 집중. DB/네트워크 의존이 있으면 단위 테스트가 아니다.
- **통합 테스트**: 실제 또는 테스트용 외부 의존성(DB, API)을 사용해 repository/service 계층의 실제 동작을 검증. 여기서 과도하게 mock하면 실제 오류를 못 잡는다.
- **E2E**: 핵심 경로만 — 모든 흐름을 E2E로 덮으려 하지 않는다.

## Mock 기준

- 외부 서드파티 API는 mock 처리한다 — 테스트가 외부 서비스 가용성에 의존하면 안 된다.
- 자체 DB는 mock하지 않는다 — 실제 쿼리 문법 오류, 제약조건 위반은 mock으로 잡을 수 없다. 대신 테스트 전용 DB/트랜잭션 롤백 전략을 쓴다.
- 시간(현재 시각)에 의존하는 로직은 반드시 주입 가능하게 만들고 테스트에서 고정한다.

## 반드시 검증해야 할 경계면

1. **계약 경계**: 요청/응답 스키마 검증 실패 시 정확히 처리되는가
2. **부분 실패 케이스**: 중간에 실패했을 때 데이터 일관성이 깨지지 않는가 (부분 커밋/적재 여부)
3. **동시성**: 같은 리소스에 대한 동시 실행이 레이스 컨디션을 일으키지 않는가
4. **권한 경계**: 접근 권한이 없는 리소스에 대한 시도가 차단되는가

## 흔한 갭 패턴

- Happy path만 테스트하고 실패 경로(네트워크 타임아웃, 잘못된 입력, 권한 없음)가 비어있는 경우가 가장 흔하다.
- 마이그레이션에 대한 테스트가 없어 스키마 변경이 기존 쿼리를 깨뜨리는 걸 못 잡는 경우.

## 리뷰 시 체크 우선순위

1. 실패 경로(에러/권한/동시성) 테스트 존재 여부
2. Mock 사용이 적절한 경계에서 이루어지는가
3. 테스트 피라미드 비율이 뒤집혀 있지 않은가(E2E 과다, 단위 부족)

## 프로젝트 특이사항

이 프로젝트에는 REST API가 없으므로 "계약 경계"는 (1) KIS 마스터파일/응답 파싱 계약과 (2) Supabase upsert 계약으로 치환한다. "권한 경계"도 사용자 인가가 아니라 service_role 키의 RLS 우회 범위가 의도한 테이블(`etf_info`, `kis_token_cache`)로만 한정되는지로 치환한다.

현재 테스트 구성(`tests/unit/`, `tests/integration/`)은 이 원칙을 이미 따른다:
- `tests/unit/test_master_file.py` — 고정폭 파싱(순수 함수)을 mock 없이 검증. 실제 KIS 데이터로 오프셋을 검증한 이력이 있으므로(1바이트 예약 필드 발견), 새 필드 추가 시에도 합성 데이터가 아니라 실제 응답 구조 기반으로 offset을 재검증해야 한다.
- `tests/integration/test_kis_auth.py`, `test_etf_repository.py` — Supabase/httpx 클라이언트를 mock한 경계 테스트.

갭: 부분 실패 케이스(마스터파일 파싱은 성공했지만 Supabase upsert가 배치 중간에 실패하는 경우)와 APScheduler의 `max_instances`(중복 실행 방지) 동작은 아직 테스트되지 않았다 — 이 프로젝트에서 우선순위가 가장 높은 다음 테스트 대상이다.
