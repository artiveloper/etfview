# QA Frontend Strategy

> 프로젝트 특이사항 절의 대상: `web/` 서브프로젝트. 경로 언급은 `web/` 기준 상대경로다.

특정 프레임워크·라이브러리(예: React Query 패턴 검증)에 종속된 검증 항목은 이 스킬에 넣지 않고 `react-query-guide` 등 기술 스킬로 분리한다. 이 스킬은 프레임워크 불문 테스트 전략 판단 기준만 다룬다.

## 기본 원칙 — 구현이 아니라 행동을 테스트

- 컴포넌트의 내부 state나 함수 호출 여부를 검증하는 테스트는 리팩터링마다 깨진다 — "사용자가 버튼을 누르면 화면에 X가 보인다" 같은 관찰 가능한 행동을 검증한다.
- 스냅샷 테스트는 UI가 자주 바뀌는 컴포넌트에 남용하면 "가짜 안전망"이 된다 — 구조가 안정적인 컴포넌트에만 제한적으로 쓴다.
- 셀렉터는 접근성 역할·라벨·텍스트 쿼리를 우선한다. 불가피할 때만 안정적인 test id를 쓴다.

## 테스트 레벨별 역할

- **단위 테스트**: 순수 로직(포맷터, 계산 함수)
- **컴포넌트 테스트**: 사용자 상호작용(클릭, 입력) → 화면 변화. API는 mock.
- **E2E**: 여러 페이지/컴포넌트를 가로지르는 핵심 사용자 흐름만. 모든 페이지를 E2E로 덮지 않는다.

## E2E 우선순위 선정 기준

1. 실패 시 비즈니스 임팩트가 큰 흐름
2. 여러 시스템이 연결되는 흐름 — 단위/컴포넌트 테스트로는 못 잡는 통합 문제
3. 자주 회귀가 발생했던 흐름(과거 버그 이력 기준)

## 흔한 갭 패턴

- 로딩/에러 상태 UI가 테스트되지 않는 경우(항상 성공 응답만 가정)
- 폼 유효성 검증의 실패 케이스가 비어있는 경우
- 접근성(키보드만으로 조작 가능한지)이 테스트에서 아예 빠져있는 경우 — design-system 스킬과 겹치는 영역이니 교차 확인한다.

## 리뷰 시 체크 우선순위

1. 구현 세부사항이 아니라 사용자 행동을 검증하는가
2. 로딩/에러 상태가 테스트되는가
3. E2E가 핵심 흐름에 집중되어 있는가 (과다/부족 여부)

## 프로젝트 특이사항

이 프로젝트는 로그인/결제 같은 고위험 흐름이 없는 조회 전용 ETF 정보 사이트다 — E2E 우선순위는 "검색어 입력 → 필터 조합 → 페이지네이션"이 사실상 유일한 핵심 흐름이며, 여러 시스템이 연결되는 지점은 Supabase 직접 조회(`domain/etf/apis/etf.api.ts`)뿐이다.

`react-query-guide` 3절에 따라 대부분의 데이터 조회는 `useSuspenseQuery`를 쓰므로, 컴포넌트 테스트에서 "로딩 상태"를 직접 검증하기보다 `<Suspense fallback>`이 실제로 최종 레이아웃과 맞는지(레이아웃 시프트) 확인하는 쪽이 이 프로젝트에 더 맞는 갭이다. `useQuery`(예외 케이스)를 쓰는 컴포넌트만 전통적인 `isLoading`/`isPending` 분기 테스트 대상이 된다.
