# Design System

> 프로젝트 특이사항 절의 대상: `web/` 서브프로젝트. 경로 언급은 `web/` 기준 상대경로다.

특정 UI 라이브러리(shadcn/Tailwind 등)에 종속된 규칙은 이 스킬에 넣지 않는다. 이 스킬은 라이브러리 불문 디자인 시스템 판단 기준만 다룬다.

## 디자인 토큰

- 색상, 간격, 타이포그래피, 그림자 등은 하드코딩된 값(`#3B82F6`, `16px`)이 아니라 이름 있는 토큰으로 참조되어야 한다.
- 토큰이 있어도 컴포넌트가 임의로 override하면 시스템이 무력화된다 — override 빈도가 높은 컴포넌트는 토큰 자체가 부족하다는 신호다.
- 다크모드/테마 전환이 필요하면 토큰은 값이 아니라 semantic 이름으로 정의해야 테마별 값만 바꿔 대응할 수 있다.

## 컴포넌트 재사용성 판단

- 같은 시각적 목적(버튼, 카드, 뱃지)의 컴포넌트가 여러 곳에서 독립적으로 구현되어 있으면 중복 — 하나로 통합하고 variant/prop으로 차이를 표현한다.
- 재사용 가능한 컴포넌트는 스타일과 동작을 분리한다 — 특정 페이지 전용 로직이 공용 컴포넌트에 섞이면 재사용성이 깨진다.

## 반응형 / 모바일 퍼스트

> 이 프로젝트는 `shadcn-ui` 스킬 0절(모바일 퍼스트)이 이미 MANDATORY 규칙(터치 타겟 44px, 반응형 클래스)으로 정의했다 — 아래는 그 규칙의 판단 근거이자, 위반 여부를 확인할 때 참고하는 원칙이다.

- 모든 UI는 모바일 화면을 기준으로 먼저 설계하고 큰 화면으로 확장한다.
- 인터랙티브 요소의 터치 타겟은 최소 44px 확보한다.
- 좁은 화면에서 넓은 테이블은 가로 스크롤 또는 카드 목록으로 대체한다.

## 로딩·빈·에러 상태

- 로딩 상태는 최종 콘텐츠의 **레이아웃 형태를 유지하는 스켈레톤**으로 표현한다. "불러오는 중..." 같은 단순 텍스트로 대체하지 않는다.
- 스켈레톤은 화면마다 새로 만들지 말고 공용 컴포넌트로 재사용한다.
- **빈 목록**과 **에러 상태**는 각각 명시적으로 처리한다. 로딩·빈·에러 셋을 구분해 서로 다른 UI로 보여준다.

## 상태 표현의 일관성

- 엔티티의 상태값은 **라벨과 색상(variant)의 매핑을 한 곳에서 중앙 정의**해 재사용한다.
- **색상만으로 상태를 구분하지 않는다** — 라벨(텍스트)을 함께 제공해 색각 이상 사용자도 구분할 수 있게 한다.

## 접근성 — 필수 체크 항목

1. 색상 대비가 WCAG AA 기준(일반 텍스트 4.5:1)을 만족하는가
2. 인터랙티브 요소가 키보드만으로 접근 가능한가(포커스 순서, 포커스 표시)
3. 의미 있는 마크업(버튼은 `<button>`, 제목은 `<h1>~<h6>`)을 쓰는가
4. 이미지/아이콘에 대체 텍스트가 있는가

## 리뷰 시 체크 우선순위

1. 하드코딩된 스타일 값 존재 여부 (토큰화 누락)
2. 동일 목적 컴포넌트의 중복 구현 여부
3. 접근성 필수 항목 위반 여부
4. 모바일 퍼스트·터치 타겟(44px) 위반 여부 (`shadcn-ui` 스킬 0절 MANDATORY 규칙)
5. 로딩·빈·에러 상태 처리 누락 여부
6. 상태 표현이 화면마다 제각각인지

## 프로젝트 특이사항

`components.json`으로 shadcn/ui가 설치되어 있다. shadcn은 컴포넌트를 라이브러리가 아니라 프로젝트에 직접 복사해 쓰는 방식이라, "복사 후 각자 살짝 변형"이 누적되기 쉽다 — 같은 목적의 컴포넌트가 `components/` 아래 여러 변형으로 흩어져 있는지가 이 프로젝트에서 특히 자주 나오는 중복 패턴이다.

엔티티 상태 표현(레버리지 타입 `normal`/`leveraged`/`inverse`, 자산군, 시장 구분 등 `domain/etf/types/index.ts`)이 화면마다 라벨/색상을 새로 정의하지 않고 중앙 매핑을 쓰는지는 이 프로젝트에서 실질적으로 검증 가치가 있는 항목이다.
