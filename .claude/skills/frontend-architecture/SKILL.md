# Frontend Architecture

> 프로젝트 특이사항 절의 대상: `web/` 서브프로젝트. 경로 언급은 `web/` 기준 상대경로다.

프레임워크(Next.js/Vue 등)에 무관하게 적용되는 프론트엔드 구조 원칙. **Next.js App Router 파일 컨벤션은 `nextjs-guide`, React Query query-key/options/prefetch 패턴·domain 5계층 구조·nuqs URL 상태 규칙은 `react-query-guide`가 SSoT다** — 이 스킬은 그보다 상위의, 프레임워크 불문 원칙만 다룬다.

## 상태 분류 — 가장 먼저 판단할 것

모든 상태 관리 문제는 아래 4가지 중 어디에 속하는지 먼저 분류하는 데서 시작한다:

1. **서버 상태**: API로부터 온 데이터. 캐싱/재검증 로직이 필요 — 전역 스토어에 수동으로 넣지 않는다.
2. **URL 상태**: 필터, 페이지네이션, 탭 선택 등 새로고침 시에도 유지되어야 하는 상태 — URL 쿼리 파라미터로 관리한다.
3. **폼 상태**: 입력 중인 값 — 로컬 컴포넌트 상태로 충분하다.
4. **전역 UI 상태**: 다크모드, 사이드바 열림/닫힘 등 진짜 앱 전역 상태만 전역 스토어에 둔다.

가장 흔한 결함: 서버 상태를 전역 스토어에 수동 캐싱하면서 재검증/무효화 로직을 직접 구현.

## 컴포넌트 경계

- **Presentational vs Container** 구분: 데이터를 가져오는 로직과 렌더링 로직을 분리한다.
- 하나의 컴포넌트가 너무 많은 책임을 가지면 분리 신호다. 파일이 비대해지는 것 자체도 책임 과다 신호로 본다.
- Props가 과도하게 많아지면(대략 5개 초과가 신호) 관련 값을 객체로 묶거나 컴포지션으로 분해한다.
- Props drilling이 3단계 이상 깊어지면 컴포지션(children prop) 또는 컨텍스트를 고려한다.
- 여러 곳에서 반복되는 비시각적 로직은 컴포넌트에서 분리해 재사용 단위(훅 등)로 추출한다.

## 데이터 Fetching 패턴

- 컴포넌트 마운트 시 직접 fetch하는 패턴(useEffect + fetch)은 경쟁 조건, 캐싱 부재 문제가 있다.
- 워터폴(하위 컴포넌트가 순차적으로 데이터를 요청) 발생 여부를 확인한다 — 병렬화 가능하면 상위에서 한 번에 요청한다.
- 데이터 변경(mutation)은 로딩·에러·성공 상태를 각각 처리한다. 낙관적 업데이트를 쓰면 **실패 시 이전 상태로 되돌리는 롤백 경로를 반드시 함께 설계**한다.

## 에러 경계 · 폼 검증

- **에러 경계**: 페이지/기능 단위로 렌더 에러 경계를 두어, 한 컴포넌트의 실패가 화면 전체를 무너뜨리지 않도록 격리한다.
- **폼 검증 이중화**: 검증은 클라이언트·서버 양쪽에 둔다. 클라이언트 검증은 즉각 피드백(UX)용일 뿐 신뢰 경계가 아니다.

## 폴더 구조 원칙

- **기능별(feature-based)** 구조를 기본으로 한다.
- 공통 UI 프리미티브만 별도 shared 위치에 둔다.
- 특정 feature 1곳에서만 쓰는 코드를 공용 lib/shared에 두지 않는다 — 실제 사용 범위로 위치를 판단한다.

## 리뷰 시 체크 우선순위

1. 서버 상태가 올바른 방식으로 관리되는가 (수동 캐싱 남용 여부)
2. 컴포넌트가 단일 책임을 지키는가 (props 과다·비대한 파일 여부)
3. 데이터 fetching에 워터폴/경쟁 조건이 없는가
4. 폴더 구조가 기능 단위로 확장 가능한가
5. 뮤테이션/낙관적 업데이트에 로딩·에러·롤백 처리가 있는가
6. 페이지/기능 단위 에러 경계가 있는가
7. 폼 검증이 클라이언트·서버 양쪽에 있는가

## 프로젝트 특이사항

이 프로젝트의 폴더 구조 원칙은 `react-query-guide` 스킬 1절이 이미 훨씬 구체적으로 강제한다(`domain/{feature}/{types,apis,parser,query-keys,query-options,hooks,prefetch}`, `index.ts`/`server.ts` 두 진입점) — 이 스킬의 "폴더 구조 원칙" 절은 그보다 상위의 일반 원칙으로만 참고하고, 기존 `domain/etf/` 구조를 재해석하는 데는 `react-query-guide`를 우선한다.

상태 분류 4가지 중 이 프로젝트에는 **폼 상태**와 **전역 UI 상태**가 사실상 없다(로그인/입력 폼 없는 조회 전용 사이트) — 서버 상태(React Query)와 URL 상태(`nuqs`, `react-query-guide` 6절)만 실질적으로 쓰인다. 새 코드에서 폼 상태나 전역 스토어가 등장하면 이 프로젝트의 단순한 상태 모델에서 벗어나는 것이므로 왜 필요한지부터 확인한다.

뮤테이션 롤백 원칙은 이 프로젝트에는 적용 대상이 거의 없다(쓰기 기능이 없음) — 향후 즐겨찾기 등 사용자 상호작용 기능이 추가되면 그때부터 적용된다.
