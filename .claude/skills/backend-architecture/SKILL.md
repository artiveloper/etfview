# Backend Architecture

> 프로젝트 특이사항 절의 대상: `collector/` 서브프로젝트. 경로 언급은 `collector/` 기준 상대경로다.

스택에 무관하게 적용되는 백엔드 구조 원칙. 언어별 세부 컨벤션은 `python-guide` 스킬을 참고하고, 이 스킬은 구조적 판단 기준만 다룬다. 특정 프레임워크·기술(예: Supabase)에 종속된 규칙은 이 스킬에 넣지 않고 별도 기술 스킬로 분리해 하네스가 매칭한다.

## 계층 분리

- **Controller/Handler**: 요청 파싱, 응답 포맷팅만 담당. 비즈니스 로직을 넣지 않는다.
- **Service**: 비즈니스 로직의 단일 소유자. 여러 리소스에 걸친 트랜잭션 경계도 여기서 관리한다.
- **Repository/DAO**: 데이터 접근만 담당. 여기에 비즈니스 규칙이 새어 들어가면(예: 조건부 필터링 로직) 서비스 계층으로 옮긴다.

판단 기준: 상위 계층은 하위 계층의 구현을 몰라야 한다(의존성은 항상 한 방향). 역방향 의존이 보이면 구조적 결함이다.

## API 계약 설계

- 응답 스키마는 소비자와 사전 합의하고, 버전 변경 시 하위 호환을 깨는지 명시적으로 판단한다.
- 에러 응답 포맷은 프로젝트 전체에서 일관되어야 한다.
- 멱등성이 필요한 작업(생성, 적재 등)은 명시적으로 표시하고 검증한다.
- 성공/에러를 구분 가능한 일관된 응답 봉투(envelope)를 프로젝트 전체에서 하나로 정한다.
- 목록 응답은 페이지네이션 메타와 결과 상한을 강제한다(무제한 조회 금지).

## 입력 검증 (경계면)

- 모든 외부 입력은 도메인 로직 진입 전, 경계에서 스키마로 검증한다. 신뢰 경계 안쪽에는 검증된 타입만 흐르게 한다.
- 검증 실패는 즉시 표준 에러 형태로 처리하고, 어떤 필드가 왜 실패했는지 알 수 있게 한다.

## 트랜잭션 경계

- 트랜잭션은 서비스 계층에서 시작하고 끝나야 한다. Repository가 자체적으로 커밋하면 여러 리소스에 걸친 원자성이 깨진다.
- 외부 API 호출은 트랜잭션 안에 넣지 않는다 — 실패 시 롤백 불가능하거나 트랜잭션이 불필요하게 길어진다.
- 긴 트랜잭션은 락 경합을 유발한다. 읽기 전용 작업은 트랜잭션 밖으로 뺄 수 있는지 검토한다.

## 에러 처리 전략

- 예외를 계층마다 다르게 잡지 말고, 하나의 중앙 에러 처리 지점에서 일관되게 변환한다.
- 비즈니스 예외와 시스템 예외(외부 연결 실패)를 구분해서 다른 로그 레벨/알림 정책을 적용한다.
- 에러를 삼키지 않는다 — catch 후 아무 처리 없이 넘어가는 코드는 결함으로 간주한다.

## 인증 / 인가

- 인증(누구인가)과 인가(무엇을 할 수 있는가)를 분리한다.
- 신원·권한은 신뢰 가능한 서버 측 소스에서만 취한다.
- RBAC 등 역할 기반 접근 제어는 한 곳에서 정의하고 재정의하지 않는다.

## 보안 기본 원칙

- 인젝션 방지: 쿼리는 파라미터 바인딩/ORM으로 작성한다.
- 시크릿 관리: 비밀키·토큰은 환경변수로 관리하고 서버 전용으로 유지한다. 런타임에 존재·형식을 검증한다.
- 민감 데이터 비노출: 내부 예외 메시지를 클라이언트에 그대로 노출하지 않는다.
- 로그 마스킹: 비밀키·토큰·PII는 평문 로깅 금지.

## 리뷰 시 체크 우선순위

1. 계층 간 의존성 방향이 지켜지는가
2. 트랜잭션 경계가 명확한가 (특히 외부 호출이 섞여 있는지)
3. 에러 처리가 중앙화되어 있는가
4. 응답/적재 계약이 일관적인가
5. 외부 입력이 경계에서 검증되는가
6. 인가·소유권 검증이 일관되게 적용되는가
7. 시크릿/민감 데이터 노출·인젝션 방지가 지켜지는가

## 프로젝트 특이사항

eft-collector에는 HTTP controller가 없다 — 계층은 `scheduler`(진입점, controller 역할) → `jobs`(service 역할, 오케스트레이션) → `infra`(repository/adapter 역할) → `domain`(순수 타입)으로 대응한다. 의존성 방향은 `scheduler → jobs → infra/domain`이며, `infra`가 `jobs`를 다시 import하면(역방향) 구조적 결함이다.

"API 계약"은 두 개: (1) KIS Open API를 **소비**하는 계약(`infra/kis/`) — 여기서는 "버전 변경 시 하위 호환"이 아니라 "KIS가 필드를 바꾸면 우리 파싱이 조용히 깨지지 않는가"가 핵심, (2) Supabase에 **적재**하는 계약(`infra/supabase/etf_repository.py`) — `upsert_many`는 멱등적이므로(같은 데이터로 재실행해도 안전) 이 멱등성이 새 job 추가 시에도 유지되는지 확인한다.

시크릿 관리는 이미 `pydantic-settings`(`config.py`)로 기동 시점 검증되고 있다 — `KIS_APP_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`가 로그에 평문 노출되지 않는지(특히 `logging_config.py`의 로그 포맷과 예외 스택트레이스)를 새 코드 추가 시마다 확인한다.
